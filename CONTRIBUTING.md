# Contributing to DisposableEvents

Thanks for helping out. This page covers how to get a change merged: branches, PR titles, labels,
and what to run locally.

New to the codebase? [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md) is the fastest way in.
Writing tests? [docs/TESTING.md](docs/TESTING.md).
Working through an AI agent? [AGENTS.md](AGENTS.md).

## Always go through a pull request

Release notes are generated by GitHub from **merged pull requests**, not from commits. A commit
pushed straight to `main` is invisible in the changelog forever — it will never appear in any
release body, and consumers reading the release notes on nuget.org will never learn it happened.

That is not hypothetical: the only commit between `v1.0.0-beta2` and today was a direct push, so the
range currently generates an empty changelog.

So: branch, open a PR, label it, merge it. Even for one-line fixes.

## Branches

Branch off `main` and name the branch after the type of change:

```
feat/subscribe-once
fix/await-next-async-cancelled-token
docs/contributing-guide
refactor/use-hcommons
chore/bump-r3
```

## PR titles are changelog lines

**Your PR title is published verbatim as a bullet in the next release.** Write it for someone
reading the release notes six months from now, not for you today.

Format is [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>: <imperative summary, lowercase, no trailing period>
```

| Type | Use for |
|---|---|
| `feat` | New public API or capability |
| `fix` | Bug fix |
| `docs` | Documentation only |
| `refactor` | Internal change with no behaviour change |
| `perf` | Performance work |
| `test` | Tests only |
| `build` | csproj, packaging, dependencies |
| `ci` | Workflows and repo automation |
| `chore` | Anything else that ships no user-visible change |

Use `feat` — not `feature`. Older history contains a `feature:` prefix; that spelling is retired.

Good: `fix: make disposing a subscription invalidated by ClearHandlers a no-op`
Not: `Fixed a bug.` / `Update EventCore.cs` / `feature: hub`

For a change that breaks the public API, add a `!` and label the PR `breaking-change`:

```
feat!: rename RegisterHandler to AddHandler in the func API
```

PRs are **squash-merged**, so the PR title becomes the commit subject on `main` with ` (#NN)`
appended. Individual commits inside your branch are not published anywhere — do not agonise over
them, but keep the PR title exact.

## Labels decide where your change lands in the release notes

`.github/release.yml` buckets each merged PR by its labels. **An unlabelled PR falls into "Other
Changes"**, which is where good work goes to be overlooked. Apply exactly one:

| Label | Release-notes section | Apply when |
|---|---|---|
| `breaking-change` | Breaking Changes | Existing consumer code stops compiling or changes behaviour |
| `enhancement` | Features | New public API or capability |
| `bug` | Bug Fixes | Fixes incorrect behaviour |
| `documentation` | Documentation | Docs, README, XML comments only |
| `dependencies` | Dependencies | Package or action version bumps (Dependabot applies this itself) |
| *(none of the above)* | Other Changes | Refactors, tests, CI, chores |

If a PR is genuinely both a feature and a breaking change, label it `breaking-change` — the
category listed first wins, and breaking is the one people must not miss.

## Building and testing locally

Any recent .NET SDK builds the solution (CI installs 9.0.x, 8.0.x, and 6.0.x). Running the *tests*
additionally needs the matching **runtimes** installed, one per test target framework — without
them the test host fails with `error run failed: ... framework ... was not found`, which is a
missing runtime, not a broken test.

```bash
dotnet restore DisposableEvents.sln
```

```bash
dotnet build DisposableEvents.sln -c Release --no-restore
```

```bash
dotnet test DisposableEvents.sln -c Release --no-build --verbosity normal
```

Those are exactly the three commands CI runs, so if they pass locally the `Test and Build .NET`
check should pass too. Tests run against `net6.0`, `net8.0`, `net9.0`, and additionally `net48` when
you are on Windows — a change can compile on `net9.0` and still break `netstandard2.0`, so build the
whole solution rather than a single project.

To run one target framework only:

```bash
dotnet test DisposableEvents.Tests/DisposableEvents.Tests.csproj -c Release -f net8.0
```

> **Windows + Git Bash / MSYS:** write MSBuild properties as `-p:Name=value`, never `/p:Name=value`.
> MSYS rewrites the leading slash into a path and MSBuild then fails with
> `MSBUILD : error MSB1008: Only one project can be specified.`

## Review and merge

- Keep a PR to one concern. Two unrelated fixes are two PRs and two changelog lines.
- Fill in the PR template, including the label checkbox.
- CI must be green.
- Merge with **Squash and merge**.

## Releases

Releases are cut manually by the maintainer.

1. Run the **Build-Release** workflow (`workflow_dispatch`) with a `version` input in plain SemVer —
   `1.0.0-beta3`, **no** `v` prefix. Set `dry-run: true` first to build, test, and pack without
   publishing.
2. A real run packs all three packages at that one shared version, pushes them to nuget.org, then
   creates tag `v{version}` and a GitHub release whose body is generated from merged PRs.
3. Any version string containing `-` is automatically flagged as a pre-release.

Each package sets `PackageReleaseNotes` to the URL of the matching release, so the nuget.org listing
links back to the generated changelog.

To preview what the notes would say before releasing:

```bash
gh api repos/Hissal/DisposableEvents/releases/generate-notes -f tag_name=v1.0.0-beta3 -f target_commitish=main -f previous_tag_name=v1.0.0-beta2 --jq .body
```

A dry run will not show you this — the release job is skipped entirely when `dry-run` is true.
